# 《离开山谷以前》Demo 迭代计划

本计划以 `DESIGN_LOCK.md` 为唯一方向依据。目标不是在现有 Demo 上增加更多文字和按钮，而是逐步替换其错误的体验骨架。

## 1. 当前 Demo 诊断

### 可以保留

- 第一人称视角
- 手机作为贯穿系统
- 拍下信件、丢失手机、归还后重看照片的结构
- Web 发布和低门槛试玩
- GPT Image 生成的山脊、森林、公路视觉基调
- 单线短篇的范围控制

### 必须替换

| 当前问题 | 修改目标 |
|---|---|
| 开场直接进入山脊 | 增加抵达、徒步、好奇心和人物建立，让它先成为一次旅行 |
| 三张背景反复调色使用 | 扩展到 12–14 张连续场景板，并拆分视差层 |
| 点击热点后瞬间换图 | 改为连续镜头推进、脚步、遮挡和身体动作转场 |
| 没有真正的冒险过程 | 加入观察路线、轻量通过、回望距离和自愿拍照 |
| 主角几乎没有身份 | 加入固定手部/服装、手机个性、相册、聊天和生活化声音 |
| 信件被当成悬疑核心 | 降为 45 秒以内的偶然插曲，删除伪造预言和神秘化包装 |
| 危险通过剧情按钮突然发生 | 让时间随探索自然流逝，由玩家主动查看地图后完成认知翻转 |
| 夜林只有三个点击点 | 制作为 8–10 分钟可玩的寻路与自救段落 |
| 获救和找手机被压缩成面板 | 制作车内相处、共同返回、公路搜索和拨号的连续场景 |
| 陌生人只是剪影和一句台词 | 设计两位普通、可信、有互动节奏的新朋友 |
| 手机归还过于神秘化 | 使用普通环境、普通动作和停顿表现毫无预兆的归还 |
| 结局用文字直接解释主题 | 改为查看玩家自己的相册、想起信件、安静离开 |
| 环境只有程序噪声 | 建立随地点和身体状态变化的声音层 |

## 2. 迭代原则

1. 每轮只验证一个核心假设，不同时铺开所有内容。
2. 先用灰盒和临时素材验证行走、拍照、时间推进和情绪节奏，再批量生成美术。
3. 任何新系统必须直接服务“年轻女孩的一次冒险”；不能解释清楚其情绪功能的系统不加入。
4. 每个阶段都保持可从头运行到当前结尾，不留下无法试玩的中间状态。
5. 每次线上更新保留版本标签和简短试玩问卷。

## 3. 阶段计划

### 阶段 0：设计冻结与代码基线

状态：当前阶段。

工作：

- 将设计锁定和迭代计划提交仓库。
- 给现有版本打 `prototype-v0` 标记。
- 保留线上旧版用于前后对比，不在其结构上继续堆功能。

验收：团队对“角色化第一人称 2.5D 旅行冒险”没有不同解释。

### 阶段 1：新体验骨架

目标：证明 2.5D 第一人称不再像幻灯片。

工作：

- 引入 PixiJS 渲染层。
- 建立数据驱动的章节 / 场景状态机。
- 完成一个三层视差山路灰盒。
- 实现有限环视、沿路线连续前进、回头和遮挡转场。
- 实现第一版手部与袖口覆盖层。
- 保留 React 手机 UI，并与场景状态双向通信。

交付切片：下车点 → 山路入口 → 第一个观景点，约 5 分钟。

验收：

- 玩家能描述自己“走到”观景点，而不是“点击切到”观景点。
- 玩家能从手、手机和声音判断主角是年轻女性。
- 没有使用剧情文字也能理解路线关系。

### 阶段 2：冒险乐趣垂直切片

目标：在没有危险和命运内容时，游戏本身仍然好玩、好看、想继续走。

工作：

- 完成观察目标 → 选择靠近 → 轻量通过 → 得到风景的核心循环。
- 制作两种地形交互：铁索通过、碎石坡落脚。
- 实现回望已走路线。
- 实现真实构图截图与相册保存。
- 加入人物生活化自言自语、手机壳、锁屏和少量旧照片。
- 建立时间随探索、绕路和失败自然推进的规则。

交付切片：山路入口 → 两段通过 → 高处风景 → 发现并拍下信件，约 12–15 分钟。

验收：

- 至少 70% 的测试者在没有任务要求时主动拍摄两张以上照片。
- 玩家首先把体验称为“旅行 / 冒险”，而不是叙事点击游戏。
- 玩家喜欢主角的陪伴感，但不觉得她说话过多。
- 信件不会让多数玩家提前判断游戏是灵异或解谜题材。

### 阶段 3：危险认知与自救

目标：让同一座山从美丽自然地转化为危险，同时保留主角主动性。

工作：

- 制作实时光线从下午到日落的变化。
- 让玩家主动打开地图、时间和电量后意识到处境。
- 制作夜间手电、路线搜索、滑倒与恢复。
- 用呼吸、手部、脚步和自言自语表现恐惧，不加入怪物。
- 实现手机在摔倒后无提示遗失，直到安全后摸口袋才被发现。

交付切片：高处平台 → 察觉危险 → 夜间下山 → 抵达公路，约 10–12 分钟。

验收：

- 玩家能指出是自己的探索时间和路线判断形成了危险。
- 玩家感到害怕，但不把游戏识别为恐怖游戏。
- 玩家认为自己完成了自救，而不是等待剧情救援。
- 手机丢失的发现无需文字提示也能被理解。

### 阶段 4：普通人的温度

目标：让陌生人的帮助成为现实层面的情感核心。

工作：

- 设计两位救援者 / 新朋友的性格、关系和对话节奏。
- 制作公路求助与判断是否信任的轻交互。
- 制作车内暖风、递水、松弛和恢复说笑的段落。
- 制作共同返回搜索：慢速行车、观察路面、下车寻找、借手机拨号。
- 让重复搜索同时推进人物关系，避免任务化刷点。

交付切片：公路获救 → 车内交流 → 返回寻找 → 确认找不到，约 10–12 分钟。

验收：

- 玩家记得两位帮助者的性格，而不只记得“NPC救了我”。
- 玩家认为他们成为朋友是自然发生的。
- 找不到手机带来真实遗憾，但没有压倒冒险整体的温暖。

### 阶段 5：接受、归还与余韵

目标：让最后的奇妙来自无法解释的普通巧合，而不是悬疑揭晓。

工作：

- 制作主角主动安慰自己并接受损失的安静段落。
- 设计手机被普通地递回手中的第一人称动作。
- 恢复玩家自己拍摄的全部照片。
- 让玩家在相册里自然重新看到信件。
- 删除解释命运的结尾旁白，仅保留极少反应和离开山谷的声音 / 画面。

交付：从放弃寻找到完整结局，约 4–5 分钟。

验收：

- 玩家描述手机归还为“巧”“幸运”“世界很温柔”，而不是超自然。
- 多数玩家会在相册中停留并回看自己的旅行照片。
- 玩家在没有解释的情况下自行把信件与经历联系起来。

### 阶段 6：完整内容、美术与声音统一

目标：把验证通过的灰盒扩展为 35–50 分钟完整短篇。

工作：

- 按统一角色和环境参考使用 GPT Image 制作 12–14 张场景板。
- 为每张主场景拆分前景、中景、远景和动画元素。
- 完成手部、袖口、鞋、手机和饰品的一致性资产。
- 完成环境声音、身体声音、车辆和手机声音。
- 增加章节存档、继续游戏、字幕和减少动态选项。
- 优化 WebP、纹理尺寸、首屏加载和低端设备性能。

验收：

- 完整游玩时长中位数 35–50 分钟。
- 首次加载与场景切换无明显阻塞。
- 所有场景中角色身体和手机视觉一致。
- 不依赖临时文字说明完成故事理解。

### 阶段 7：三轮定向试玩

#### A 轮：形式验证（5–8 人）

只测试前 15 分钟。验证它是否首先被感知为一次年轻女孩的旅行冒险。

#### B 轮：情绪验证（8–12 人）

测试完整灰盒。记录危险意识、获救、放弃和归还四个节点的口述反应。

#### C 轮：陌生玩家验证（15–30 人）

不提供主题说明，只给出游戏下载链接。通过问卷确认玩家是否自行产生“被世界善待”的表达。

最终放行标准：

- 80% 以上玩家首先将作品描述为旅行 / 冒险。
- 70% 以上玩家能描述主角的年龄感和两个以上性格特征。
- 70% 以上玩家在手机归还时使用“巧、幸运、温暖、奇妙”中的至少一种近义表达。
- 少于 15% 的玩家把事件解释为明确超自然现象。
- 少于 15% 的玩家认为前半段只是为后续剧情服务的冗长铺垫。

## 4. 推荐执行顺序

不要立即重做完整剧情。下一次开发只执行阶段 1，并以 5 分钟新切片替换当前 Demo 的开场。阶段 1 未通过“走到而非点到”的验证前，不生成后续批量美术，也不制作救援和结局。

阶段 2 是项目的生死检查点：如果没有危险、手机丢失和命运结尾时，玩家仍不享受与她一起探索，说明主体体验尚未成立，必须继续修改冒险循环，而不能依靠后半段剧情补救。
